# TinyPDF 支付发布整合设计（2026-10-27）

## 目的与边界

在已上线的邮箱登录和首页版本上接入预购压缩次数：1、3、5、10 次，同一个已验证邮箱账号跨设备恢复余额；仅成功压缩消耗一次。保留现有登录接口、Cookie、账号 ID、中文/英文弹窗和匿名首免费行为。上线前收费双开关保持关闭。本次不启用邀请奖励，也不把旧版“先压缩再购买结果”带回公开流程。

## 整合方案

采用线上 `auth_accounts` 与 `auth_sessions` 作为唯一账号身份。支付预览版的 `email_accounts`、`email_account_sessions` 和重复的 `/api/auth/*` 实现只作为迁移参考，不能在正式运行时与线上账号系统并存。新增账号到钱包的一对一映射，所有已购次数、订单及退款仅以已验证账号 ID 授权查询。游客钱包只提供首免费，退出登录后不得读取账号已购次数；同一邮箱重新登录后余额不变。数据库迁移必须可重复执行、不得删除现有登录会话或历史数据。若既有支付预览库已产生测试账号，先做只读审计再决定数据迁移，不能按邮箱静默合并不同身份。

购买页面沿用已验收的四档数量、¥9.90 / $1.99 单次基础价和本地化文案；实际金额以 Paddle Checkout 为准。完整 Paddle `txn_` 单号在订单页和支付管理后台可见。交易完成只由签名 Webhook 或服务端向 Paddle 核对后入账，重复事件不得重复加次数。整单次数未用可发起原路全额退款并先冻结权益；已经使用任一次则转人工审查，不自动全额退款。退款申请中、批准、拒绝、到账/最终状态不得混称。失败、超时或目标区间不合格的压缩不扣次数。

## 方案取舍

- **选用：以当前线上登录为主，移植购买、钱包和退款模块。** 保留已发出的登录会话，发布风险最低；需要改造旧支付模块的账号外键和授权入口。
- 不选：直接合并旧支付预览分支。试合并出现双份登录接口和不同账号表；虽然 Git 文本冲突少，运行时却可能造成余额错绑。
- 不选：用邮箱字符串直接作为钱包主键。未经验证的邮箱不能作为支付权益凭据，也会增加串号风险。

## 发布门槛

1. 干净隔离分支完成整合；现有登录回归、购买/退款回归、真实 PDF 压缩回归及桌面/手机浏览器流程全绿。
2. 独立沙盒数据库完成全部迁移、并发、重启恢复和重复事件测试；不得直接把试验迁移施加到生产库。
3. Paddle 沙盒商品/价格、测试客户端令牌、服务器 API key 和通知端点配置齐全；真实沙盒 Checkout、签名 `transaction.completed`、`adjustment.created/updated`、失败付款和退款回执端到端通过。
4. Paddle 正式账户身份和 `tinypdf.cn` 网站审核通过；支付宝可用性另行核实。正式凭据与沙盒凭据不得混用。
5. 先部署收费关闭版并验收登录和免费压缩；用户确认后才开启正式收费。可通过关闭收费开关停止新订单，但保留既有订单、权益、退款和 Webhook 处理。

## 当前事实与限制

2026-10-27 的支付分支完整单元/接口测试以及 25 项浏览器模拟流程通过，但它未与当前线上登录系统整合，也未完成真实 Paddle 沙盒扣款、Webhook 与原路退款联调。当前本机没有 Paddle 沙盒凭据或独立 PostgreSQL 测试库；这些缺口不应通过使用生产密钥或生产数据库代替。
