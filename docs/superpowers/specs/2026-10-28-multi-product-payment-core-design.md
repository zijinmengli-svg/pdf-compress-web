# 多产品支付核心设计（2026-10-28）

## 意图与现状

TinyPDF 即将以 Paddle 销售 1、3、5、10 次压缩机会。用户希望这次建设的支付能力以后也能服务其他产品，不把商品、账号和权益规则写死为 TinyPDF；同时尽量少增加当前开发与运维成本。

当前支付分支尚未对外启用：`lib/payment/credit-purchase.js` 把 TinyPDF 账号 ID、钱包哈希、单个 Paddle 商品/价格、购买次数、压缩次数入账和退款写在一起；`config.js` 只有一组 `PADDLE_PRODUCT_ID`/`PADDLE_PRICE_ID`；`credit_purchases` 与 `reward_ledger` 分别记录交易和次数。这一分支仍缺独立数据库与真实 Paddle 沙盒端到端验收，不得因本设计直接开启正式收费。

## 目标、非目标与不可接受结果

- 目标：一套部署于现有 Node 服务中的可复用支付核心，TinyPDF 是第一个产品；以后新增产品通过受控商品配置、身份适配器和权益适配器接入，不复制 Paddle Webhook、订单与退款基础设施。
- 目标：按产品隔离订单与权益，保留 TinyPDF 当前登录、匿名首免费、仅压缩成功扣次数、购买数量选项和中英文页面行为。
- 目标：订单能追踪购买者、产品、套餐、实付金额/币种、Paddle 交易及退款状态；后台可按产品和订单查询。
- 非目标：本期不建独立支付微服务、统一用户账号中心、多产品购物车、订阅、邀请奖励，也不为尚不存在的第二产品制作前端。
- 不可接受：A 产品付款给 B 产品发权益；浏览器回调或自报邮箱即可入账；重复 Webhook 重复发放；退款失败后权益永久冻结却没有待人工处理状态；未完成沙盒/审批就打开收费。

## 方案取舍

1. **选用：现有 Node 应用内的多产品支付核心。** 将订单、商品目录、Paddle 适配、事件处理、退款状态做成通用模块；TinyPDF 的账号解析和压缩次数账本做产品适配器。它复用当前开发成果，成本与上线风险较低，未来可提取为包或独立服务。
2. 独立支付服务：跨项目共享最直接，但现在就需要服务间认证、网络部署、独立运维及一致性处理；在只有一个产品时过重。
3. 为每个产品复制 TinyPDF 支付代码：眼下最快，但支付安全修复、退款与对账会分叉，违背复用目标。

用户选择方案 1。以下接口命名、表结构细节及迁移顺序属于实现选择，由开发按测试结果微调，不代表用户另行指定。

## 模块边界

### 支付核心

核心只认识稳定的 `product_key`、`offer_key`、经服务端验证的 `subject_namespace + subject_id`、订单、支付提供方和权益适配器；不读取 TinyPDF 的 `auth_accounts`、`reward_wallets` 或压缩任务表。它负责：

1. 服务端商品目录：每个产品列出可售套餐、环境对应的 Paddle product/price ID、允许数量、启用状态。客户端只能提交公开的产品/套餐键和允许数量，不能决定价格 ID、金额或身份。
2. 订单：创建不可变订单号和购买意图；订单记录产品、套餐、购买者、预期数量、环境、实付金额/币种、Paddle `txn_` 及状态。首版一个 Paddle 交易仅对应一个产品的一个套餐；未来的跨产品购物车不属于本期。
3. Paddle 适配：创建 Checkout 所需条目/服务端交易，签名验证原始 Webhook，将异步事件持久化去重，并向 Paddle 读取交易/退款作为权威状态。浏览器支付成功事件只触发状态查询，不直接发权益。
4. 核验与履约：从签名购买引用定位服务端订单，核对交易环境、交易 ID、实际商品/价格、实际数量及已支付总额/币种；在数据库事务和唯一约束下将订单标为已支付并调用产品权益适配器，重复或乱序事件不得二次发放。若 Checkout 允许买家修改数量，以 Paddle 实付数量为准，且必须处于服务端定义的允许范围；否则进入异常待人工核对，不自动发放。
5. 退款：管理员经现有后台鉴权以订单号或 Paddle 交易号发起；先询问产品适配器可否自动撤销权益，再提交原路退款。分别记录申请中、审核中、批准、拒绝、已完成/需人工处理；Paddle 返回不确定时不得盲目重试。退款事件同样去重。支付核心不擅自定义所有产品的“已使用”含义。
6. 查询与审计：用户只能查询已验证且与其身份绑定的本产品订单；后台可跨产品筛选并查看操作与状态历史。日志不记录 API 密钥、验证码、完整邮箱或卡信息。

### 产品适配器

每个产品提供：

- 身份解析：从该产品自己的已验证服务端会话得到 `subject_namespace + subject_id`。不接受客户端传来的账户 ID/邮箱作为授权凭据。不同产品不必共用 TinyPDF 登录系统；同一邮箱也不自动并号。
- 权益发放及撤销：例如 TinyPDF 将实付次数写入现有 `reward_ledger`，仅成功压缩扣一次；未来产品可实现其他数字权益，不强制使用压缩次数钱包。适配器操作与订单状态更新必须具备事务一致性或可重试的幂等机制。
- 退款策略：TinyPDF 整包未用可自动申请全额退款并冻结次数；只要使用过一部分就转人工核验，不自动全额退。退款被拒绝或撤回时可幂等恢复冻结的未用权益；已确认退款不能恢复。其他产品提供自己的规则。
- 公开页面配置：该产品的套餐文案、本地化文本及入口；通用支付核心不决定产品 UI。

TinyPDF 首版沿用一条 Paddle 单价商品/价格，1、3、5、10 是该价格的购买数量，不是四个单独价格。经核验的实付数量 1:1 发放压缩次数。未来套餐可定义自己的权益单位映射，但必须在服务端商品目录中显式配置并在订单中保留快照，不能由客户端声明。现有账本按到期时间、创建时间升序消耗，欢迎次数与多笔购买均沿用此顺序；每笔购买单独有 `purchase:<transaction_id>` 来源，因此退款只检查对应那一包的原始数量与剩余数量是否相等，不看用户总余额。

对 Paddle 后台直接发起的整单退款，即使不是 TinyPDF 后台发起，也按已核验的退款事件冻结/撤销该订单尚未消耗的权益并标记审计；若已部分使用，则转人工处理，不能静默倒扣其他包。部分退款、拒付及未知 adjustment 本期不自动按比例撤销次数，必须隔离为待人工处理，并禁止这笔订单的剩余权益继续消费，直至人工核对与明确处置；不能因为自动处理失败而丢弃事件。发放核验允许合法税费与 Paddle 折扣改变总价，但必须核对实付总额为正、币种有效、商品/价格/数量匹配，不用网页展示的固定单价反推实付金额；优惠券是否在 Checkout 提供由具体产品开关控制。

## 数据与兼容

新增通用订单/事件层（暂名 `payment_orders`、`payment_order_events`），至少持久化 `order_id`、产品/套餐键、购买者命名空间与 ID、provider/environment、价格和数量快照、实付金额/币种、provider transaction/adjustment ID、履约与退款状态、时间戳。数据库唯一约束覆盖 `provider + environment + transaction_id`、事件 ID 和每笔订单的一次性权益发放。商品目录可先在服务端配置/数据库中注册，不由前端任意新增。

保留 TinyPDF 的 `auth_accounts`、`auth_sessions`、游客欢迎次数和 `reward_ledger` 语义。当前未发布的 `credit_purchases` 可在隔离测试库中迁移到通用订单结构；在生产数据库执行前先只读核对表是否存在数据，制定可重复、仅追加或可回滚的迁移。任何历史已付款订单都不能因重构丢失关联或重复入账，不能按邮箱猜测映射。关闭新购买的开关不影响历史订单查询、Webhook、对账和退款。沙盒与正式环境的密钥、目录和交易唯一性完全隔离。

## 外部契约与接入路径

推荐由核心暴露服务端操作：`prepareCheckout({productKey, offerKey, quantity, verifiedSubject})`、`getOrder(...)`、`requestRefund(...)`、`handleProviderEvent(...)`；HTTP 路由只是薄层。TinyPDF 可保留现有 `/api/credits/*` 接口作为兼容外观，内部调用核心。以后一个新产品接入时：注册稳定产品键和套餐及其 Paddle 沙盒/正式商品价格；提供该产品的身份与权益适配器；接入共享 Webhook/订单查询；再制作自己的购买入口与测试用例。独立站点若不与 TinyPDF 共用 Node 部署，仍需安全部署核心代码或服务接口、配置回调域名和账号鉴权；“可复用”不等于无代码一键接入。

Paddle 的 Checkout 条目由价格 ID 与数量组成，`customData` 可关联订单，但服务端仍须按 Paddle 实际交易条目核验，因为结账中的条目/数量可能变化。退款及权益发放都以经核验的服务端状态为准。

## 验收与发布门槛

- 单元/集成：双产品模拟适配器，验证相同 subject ID 在不同 namespace/product 下不串订单或权益；缺失/禁用套餐失败关闭；数量篡改、价格 ID 不匹配、跨环境交易和伪造购买引用不得入账。
- 事件：重复、乱序、延迟及重启恢复；一个交易只能创建一笔订单、一次履约；退款批准/拒绝/不确定返回均不重复撤销或恢复权益。
- TinyPDF 回归：登录/游客首免费、1/3/5/10 次购买、成功压缩扣一次、失败不扣、跨设备余额、订单显示、整包未用退款、部分使用转人工。
- 环境：独立本地 PostgreSQL/沙盒库完成迁移和并发测试；Paddle 沙盒真实 Checkout、签名事件及退款回执端到端通过；生产资质与网站审核单独核实。正式收费仍需独立发布闸门，默认关闭。

## 留给实现者的决定

在不改变上述外部语义的前提下，选择静态注册表还是受控数据库目录、精确 SQL 迁移形式和模块文件名；优先复用当前 Webhook 队列与 TinyPDF 账本。实现前先写失败测试，再逐步替换 TinyPDF 专有入口，避免一次性重写支付链路。
