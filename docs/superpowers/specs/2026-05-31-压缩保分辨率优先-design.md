# TinyPDF 压缩重构：保分辨率优先 — 设计文档

**日期：** 2026-05-31
**目标（一句话）：** 在用户给定的目标大小（上限，绝不超过）以内，输出当前能做到的最高清 PDF；**优先保住图片原生分辨率，JPEG 质量为辅**。

---

## 1. 背景与现状 bug

工具面向设计师，核心痛点：作品集要压到招聘网站要求的 ≤20MB，但高清设计图模糊会让作品降级。

现状 `qfactorSearch`（`server-simple.js`）有两个致命点：

1. 图片分辨率上限**写死 300 DPI**（`runGsQf(inputPath, out, qf, 300)`），只调 JPEG 质量一个旋钮。
2. 一旦最高质量结果 ≤ 目标就**早返回**（`if (sBest !== null && sBest <= targetBytes) return best;`），浪费目标内的剩余预算。

## 2. 实测依据（用户真实文件，已验证）

测试文件：`资深体验设计师-李彬-作品集-社交版.pdf`（**71.55MB**）→ 目标 20MB。

| 发现 | 数据 |
|---|---|
| 图片原生分辨率很低 | 分辨率档 300→136 DPI 体积纹丝不动（27.47MB），72 DPI 才降到 17.32MB ⇒ 原生 ≤ ~136 DPI |
| (B) 保质量降分辨率 | 72 DPI @ q≈93 → 19.68MB / 71s。**模糊可见** |
| (A) 保分辨率降质量 | 原生 ~130 DPI @ q≈80 → 20.04MB / 42s。**用户在多个文件上确认更清晰** ✅ |

**关键 Ghostscript 参数（实测结论）：**
- 必须显式加 `-dColorImageDownsampleThreshold=1.0`（及 Gray 版）。否则 `/prepress` 默认 1.5，分辨率 cap 在很多文件上根本不生效。
- `setdistillerparams` 里的 `QFactor` 确实生效（实测改变体积），保留现有写法。
- `threshold=1.0` + 高 cap 的语义 = **保住原生分辨率、绝不上采样**，只有真·超高清图（res > cap）才被下采样。

**决策：锁定 A 策略（保分辨率优先）。** 分辨率是清晰度的主导项；q80 的 JPEG 痕迹通常肉眼难辨，72 DPI 的模糊藏不住。

## 3. 目标算法

`compressPdf` 的压缩主流程，按顺序：

1. **原样放行**：`originalBytes ≤ targetBytes` → 近乎无损复制原文件。文案"原文件已达标，原样保留"。
2. **主路径 · 保分辨率搜质量**：cap = `RES_CEIL`(600) + `threshold=1.0`，在 JPEG 质量维度搜索，找出"**质量最高（qf 最小）且 ≤ 目标**"的一档，贴目标下沿。
   - 若最高质量 `QF_BEST` 在 600 cap 下已 ≤ 目标 → 直接返回（全分辨率近无损，无法更优）。
   - 否则在 `[QF_BEST, QF_FLOOR]` 间用幂律预测搜索收敛。
   - 若连质量地板 `QF_FLOOR` 在 600 cap 下仍 > 目标 → 返回 null（信号：分辨率太高，需下采样）。
3. **分辨率兜底**（仅当主路径返回 null）：沿 cap 阶梯 `[450,300,220,150,100,72]` 自高到低，对每个 cap 重跑主路径搜索；**取第一个能在质量地板内 ≤ 目标的 cap**（= 还能塞进目标的最高分辨率）。仍是矢量管线，文字不栅格化。
   - 该路径对用户作品集**不会触发**，是给极端高清大图准备的。
4. **最低分辨率仍超 → 尽力而为**：在最低 cap(72) 放开质量到 `QF_WORST`(3.0) 取 ≤ 目标的最小结果（矢量、文字仍清晰，优于栅格化）。
5. **栅格化兜底**（极少）：上述全部拿不到 ≤ 目标 → 栅格化每页为 JPEG 重组（现有 `forceRasterToTarget`），并标记 `rasterized=true`，文案明确告知"已无法在不明显降质下达标"。
6. **绝不比原文件大**：最终结果 ≥ 原文件 → 回退原文件（现有逻辑保留）。

**全程进度文案**：主路径/分辨率兜底显示"正在尝试符合要求的最高清版本…"；栅格化路径显示自己的文案。

## 4. 常量

| 常量 | 值 | 说明 |
|---|---|---|
| `RES_CEIL` | 600 | 分辨率上限（DPI）。普通文件＝保原生；超高清图收到 600（已足够任何屏幕/下载查看） |
| `DOWNSAMPLE_THRESHOLD` | 1.0 | 让 cap 真正生效；绝不上采样 |
| `QF_BEST` | 0.02 | 最高质量（体积最大） |
| `QF_FLOOR` | 0.4 (≈q70) | **可调**。质量地板：低于此宁可降分辨率，不再降质量 |
| `QF_WORST` | 3.0 | 尽力而为路径的最低质量边界 |

## 5. 代码改动（`server-simple.js`，零依赖不变）

- **`runGsQf`**：args 增加 `-dColorImageDownsampleThreshold=1.0` 与 `-dGrayImageDownsampleThreshold=1.0`。
- **`qfactorSearch`**：
  - 接受 `resCap` 与 `qfFloor` 参数（替代写死的 300 与 QF_WORST 上界）。
  - 搜索区间变为 `[QF_BEST, qfFloor]`；找最低 qf（最高质量）的 ≤ 目标结果。
  - 质量地板内拿不到 ≤ 目标 → 返回 null。
  - **修边界步长 bug**：当结果略超目标且步长趋零时强制更大步进，确保严格 ≤ 目标、不卡在"略超"（实测曾卡 20.04MB）。
- **新增 `resolutionAwareSearch`**（或在 `compressPdf` 内联）：先在 `RES_CEIL` 跑 `qfactorSearch`；null 则沿 cap 阶梯下降重试，取最高可行 cap；最低 cap 仍不行→尽力而为；再不行→交栅格化。
- **`compressPdf`**：按 §3 顺序串联；更新进度文案为"正在尝试符合要求的最高清版本…"。

## 6. 验证计划（本地，用用户真实文件，不部署）

- `社交版 71.55MB → 20MB`：期望 ~19–19.8MB、**全分辨率（不下采样）**、≤5 分钟。
- `高清版 92.9MB → 20MB`：期望 ≤ 20MB、尽量全分辨率、≤5 分钟。
- `作品集 20.1MB → 20MB`：期望走原样放行（秒过）。
- `作品集 20.1MB → 5MB`：期望**触发分辨率兜底**，输出 ≤5MB、矢量、文字仍清晰。
- 不变量断言：结果**绝不 > 目标**、**绝不 > 原文件**、主路径**不栅格化**。
- 回归：现有功能测试（`/tmp/phase1-test.js` 等）仍 14/14。
